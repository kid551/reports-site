第 1 章  为什么是 Codex CLI

1.1 什么是 Codex CLI

Codex 是 OpenAI 推出的终端编程代理（coding agent），能在本地终端中读取、修改和运行代码。它是开源项目，使用 Rust 构建，运行速度快，安全性强。

核心能力：

  • 理解代码库 — 自动分析项目结构、依赖关系和代码逻辑
  • 编辑代码 — 根据自然语言指令修改文件
  • 执行命令 — 运行测试、构建、部署等终端命令
  • 沙盒隔离 — 通过 OS 级沙盒（macOS Seatbelt / Linux bubblewrap）限制代理权限

1.2 Codex CLI vs 其他编程助手

本地代码访问直接读写文件系统需要复制粘贴通过 IDE API

离线使用需要 API 连接需要网络需要网络

1.3 适合谁

  • 工程师 — 加速日常开发、调试、代码审查
  • 产品经理 — 快速原型验证、独立完成 MVP
  • 独立开发者 — 一人撑起全栈开发

第 4 章  审批模式与会话管理

4.1 四种审批模式

Codex 提供四种审批策略，控制代理的自主程度：

模式标志行为
Read-only-a untrusted只能浏览代码，所有修改需审批
On-failure-a on-failure自主执行，仅在命令失败时请求审批
On-request（默认）-a on-request在沙盒内自主工作，超出边界时请求审批
Never-a never完全自主，不请求审批

命令行使用：

# 只读模式 —— 适合代码审查
codex -a untrusted "审查最近的提交"

# 自动模式（默认）
codex "修复这个 bug"

# 完全自动 —— 合并了 auto-edit 审批 + workspace-write 沙盒
codex --full-auto "运行测试并修复失败的用例"

会话中切换：在 TUI 中使用 /permissions 命令实时切换模式。

4.2 --full-auto 快捷方式

--full-auto 等价于同时设置：

  • approval_policy = "auto-edit"
  • sandbox_mode = "workspace-write"
codex --full-auto "重构所有测试文件，使用 describe/it 结构"
安全提示：切勿将 --full-auto 与 --dangerously-bypass-approvals-and-sandbox 组合使用，除非在专用的沙盒虚拟机中。

4.3 Plan 模式：先想清楚再动手

很多人一启动 Codex 就直接让它改代码。但对于复杂任务，先规划再执行是效率最高的方式。

在 TUI 中输入 /plan 进入规划模式。此时 Codex 的行为会改变：

  • 它可以读取文件来理解代码，但不会修改任何文件
  • 它会给出详细的实现方案，包括要改哪些文件、怎么改
  • 你可以反复讨论、修改方案

Plan 模式的黄金工作流

  1. Plan 模式下描述需求，来回讨论 — 用 /plan 进入规划模式，描述你的需求。Codex 给出方案后，你可以说「第三步换个方式」「这里的库用 XXX 替换」，反复调整。
  2. 用一份详细的执行指令 — 方案大致满意后，写一份完整的执行指令，把讨论中确认的方案细节、约束条件都写进去。
  3. 切换到执行模式 — 计划确认后，退出规划模式。因为计划已经讨论充分，你可以放心地让 Codex 一次性执行完成。

这个流程的精髓在于：把纠结放在 Plan 阶段解决完，执行阶段一气呵成。边做边改、反复返工是最浪费 tokens 的用法。

什么时候该用 Plan 模式

用 Plan 模式跳过 Plan，直接做
你不确定实现方案改一行代码、修个 typo
需要改动多个文件加一行 console.log 调试
你对这块代码不熟悉你很清楚要改什么
重构或架构级别的变更跑个测试、装个包
第一次接触一个新项目重复性的日常操作
一条实用判断标准：如果你需要跟同事解释才能让他做的任务，就值得用 Plan 模式。如果你能用一句话说清的任务，直接做就行。

4.4 Git 操作：Codex 天然就懂

Codex 对 Git 的理解不只是帮你跑 git 命令。它真的知道你项目当前的版本控制状态，知道你改了哪些文件、在哪个分支上。

一句话 commit 和 PR

最常用的操作：

# 让 Codex 自己看看改了什么，写一个 commit message
提交当前的改动，写一个有意义的 commit message

# 或者更具体一点
commit 这些变更，描述清楚我们添加了 RSS 抓取功能

# 直接创建 PR
创建一个 PR，标题和描述写清楚这个功能的作用

Codex 会分析你的代码变更，生成一个描述性的 commit message，然后执行 git add + git commit。创建 PR 时它还会自动生成 PR 描述，包括改了什么、为什么改。

多实例并行：隔离的工作目录

如果你同时修一个 bug 的同时，想让 Codex 在另一个分支做一个新功能，可以利用不同的工作目录。Codex 在一个目录工作不会影响另一个，两件事互不干扰。

# 在一个终端窗口
cd ~/project && git checkout -b fix/login-bug
codex "修复登录页面的 token 过期问题"

# 在另一个终端窗口
cd ~/project-feature && git checkout -b feat/dashboard
codex "实现新的 dashboard 页面"

多个 Codex 实例可以同时跑不同的任务，每个在自己的目录和分支上工作。这就是 Agent 式工作的威力：你不需要自己做所有事，你管理一群 Agent 帮你做事。

4.5 --dangerously-bypass-approvals-and-sandbox

完全跳过所有安全限制，仅用于隔离环境（如 CI 容器）：

# 仅在 CI 环境中使用！
codex --dangerously-bypass-approvals-and-sandbox "部署到测试环境"

4.6 --full-auto 的安全考量

用了一阵 Codex 之后，你大概已经体会到那种「烦躁感」了。每次写文件要确认、运行命令要确认、装个依赖也要确认。频繁审批容易导致审批疲劳，让安全机制形同虚设。

--full-auto 就是为了解决这个问题。它在沙盒保护（workspace-write）下让 Codex 自主工作，通过 OS 级沙盒（macOS Seatbelt / Linux bubblewrap）限制文件系统和网络访问，而不是依赖逐个操作的人工审批。

沙盒保护了什么

在 --full-auto 模式下，沙盒会限制：

  • 文件系统 — Codex 只能写入工作目录内的文件，无法修改系统文件或其他项目
  • 网络 — 默认阻止网络访问，防止数据外泄或未授权的外部请求
  • 子进程 — 所有由 Codex 启动的子进程（git、npm、测试运行器）都继承相同的沙盒限制
注意：沙盒限制的是文件系统和网络层面的操作，但无法阻止所有类型的风险行为。操作生产数据库、管理云基础设施这类事情，还是用 -a untrusted 手动确认比较踏实。--full-auto 最适合日常开发：写代码、跑测试、Git 操作。

4.7 Computer Use：AI 长了眼睛和手（桌面应用功能）

注意：Computer Use 是 Codex 桌面应用（通过 codex app 启动）的功能，不是 CLI 的功能。CLI 支持通过 -i 参数附加图片进行分析，但不具备鼠标键盘控制能力。

前面讲的所有工作流，Codex 都是在文本世界里操作的：读代码、写代码、跑命令行。文字处理这块它确实强，但你桌面上那个 Figma 窗口、那个 Photoshop、那个只有 GUI 没有 API 的老旧管理后台，它碰不到。

Codex 桌面应用的 Computer Use 功能让 Codex 直接看到屏幕截图，然后操控鼠标和键盘。

怎么用

通过 codex app 启动桌面应用后，Computer Use 功能可用。Codex 在工作过程中如果判断需要操作 GUI，它会截一张屏幕截图来「看」当前画面，然后决定下一步该点哪里、该输入什么。

# 让 Codex 看看当前屏幕上的东西
看一下我屏幕上的这个页面，告诉我布局有什么问题

# 让它操作一个 GUI 应用
打开系统偏好设置，把暗色模式关掉

# 测试你正在开发的 Web 应用
在浏览器里打开 localhost:3000，走一遍注册流程，看看有没有 bug

当前的限制

  • 慢。每一步操作都需要截图→分析→决定→执行，一个人类 0.5 秒完成的点击，Codex 可能需要几秒钟
  • 精细操作不靠谱。拖拽一个滑块到精确位置、在一个密密麻麻的表格里选中某个特定单元格，这类操作它经常偏
  • 不适合需要快速反应的场景。动画、实时交互、游戏测试，Codex 的反应速度跟不上
核心建议：Computer Use 现阶段最好的定位是：把它当成一个耐心但手速慢的测试员。给它那些「按照固定流程重复操作」的任务，它做得很好。需要灵活判断和快速反应的，还是自己来。

4.8 Voice Mode：开口说话就能编程（桌面应用功能）

注意：Voice Mode 是 Codex 桌面应用的功能，不是 CLI 的功能。

在 Codex 桌面应用中，可以使用语音模式。Codex 会把语音转成文字，然后像正常输入一样处理。

什么时候用语音比打字好

  • 手不方便的时候。走路想到一个 bug 的修复思路、做饭时突然想起一个需求。掏出手机说一嘴，比找键盘快
  • 脑暴的时候。想法咋咋地冒，打字速度跟不上大脑。语音可以一口气把一段混乱的思路倒给 Codex，让它帮你理成结构化的需求
  • 描述空间和视觉概念的时候。「我想要一个左边是侧边栏、右边分上下两栏、上面是图表下面是表格」，话说出来比画 ASCII 图快多了
一个实用的组合：语音快速启动任务（「帮我做个 XXX」），然后切回键盘输入精确的细节和约束条件。两种交互方式混着用，比纯用一种效率高。

4.9 会话管理：别让上下文变成垃圾场

Codex 有上下文限制。对话越长，Codex 对当前任务的注意力越分散。会话管理比你想象的重要得多。

核心命令速查

操作命令/快捷键什么时候用
清空当前会话/clear切换到完全不相关的任务时
压缩上下文/compact会话太长、Codex 开始变慢或遗忘
恢复上次会话codex resume --last终端不小心关了，想继续
分叉会话/fork想在当前上下文基础上尝试不同方向

/clear 的使用时机

/clear 会清空当前会话的所有对话历史，回到一个干净的起点。AGENTS.md 和项目文件不受影响。什么时候该用？当你要开始一个和之前对话完全不同的任务时。

比如你刚才在修一个 API 的 bug，现在想让 Codex 帮你写一个新的前端组件。如果不 clear，Codex 的上下文里还残留着大量关于那个 API bug 的信息，会干扰它对新任务的理解。

/compact 的妙用

/compact 不是清空对话，而是让 Codex 把当前对话压缩成一个摘要。适合在一个长会话中途使用：你和 Codex 已经讨论了很多，上下文太长影响了性能，但你不想丢掉讨论的结论。/compact 会保留关键信息，释放上下文空间。

实用经验：不要过度依赖 /compact（自动压缩）。它是不透明的、容易出错的。需要重启时用 /clear，不要用 /compact。

4.10 六个坑，你大概率会踩

使用 Codex 时最常见的错误。这些坑不管用什么 AI 编程工具都一样。

坑 1：一个会话什么都塞

修 bug、加功能、重构代码、写文档，全在一个会话里做。上下文被塞满，Codex 对每个任务的理解都很浅。

一个会话聚焦一个任务。做完就 /clear，或者开新终端窗口。

坑 2：反复纠正，越改越偏

Codex 做错了一步，你纠正；改了又错另一个地方，再纠正；第三次还是不对。你花在纠正上的时间比自己动手还多。

纠正两次不行，果断 /clear 重来。重新描述需求，这次说得更具体。在一个已经跑偏的对话上修补，远不如推倒重来。

坑 3：看着像对的就接受了

Codex 写了一大堆代码，输出看着挺合理，你就接受了，没实际跑一下。过几天发现边界情况的 bug。

每一轮改动都实际运行一次。「代码看起来对」和「代码是对的」差距可能很大。给 Codex 一种验证工作的方式。你自己也一样。

坑 4：过度微操

Codex 每写一个文件你都要看、每改一行代码你都要评论。结果你和 Codex 都很慢，而且你其实在用 Codex 做传统编程。

关注结果。让 Codex 把一个完整任务做完，看最终输出是否符合预期。中间过程除非明显跑偏，不用管。

坑 5：需求模糊，然后怪 Codex 不懂你

「帮我优化一下这个代码」「让这个页面好看点」。Codex 只能猜，而它猜的方向很可能不是你想要的。

给具体的、可验证的需求：「把这个 API 的响应时间从 2 秒优化到 500ms 以内，瓶颈在数据库查询，考虑加缓存或优化 SQL」。越具体，输出越接近预期。

坑 6：不写 AGENTS.md

项目根目录没有 AGENTS.md，或者有但从不更新。每次新会话都要重新解释项目背景、代码规范、技术选型。

这个太重要了，整整一章来讲。翻到 §05。

这一章的核心：四种审批模式选对安全等级，会话管理保持上下文干净。这些工作流覆盖 90% 的日常场景。

第 5 章  AGENTS.md：给 AI 写规则

5.1 什么是 AGENTS.md

AGENTS.md 是给 Codex 的项目指令文件，类似于给人类写的 README，但读者是 AI。Codex 在每次启动时自动读取这些文件，用于理解项目规范和约束。

AGENTS.md 已经成为由 Agentic AI Foundation（AAIF，隶属于 Linux Foundation）管理的开放格式，被超过 60,000 个开源项目采用。

5.2 文件发现机制

Codex 按以下优先级查找指令文件：

全局级别（~/.codex/）：

  1. AGENTS.override.md（如果存在）
  2. AGENTS.md

每个目录级别只使用第一个非空文件。

项目级别（从 Git 根目录到当前工作目录）：

逐级向下查找，每级检查：

  1. AGENTS.override.md
  2. AGENTS.md
  3. project_doc_fallback_filenames 中配置的备选文件名
my-project/
├── AGENTS.md                    # 项目全局规则
├── src/
│   └── AGENTS.md                # src 目录的补充规则
└── services/
    └── payments/
        ├── AGENTS.override.md   # 支付模块的覆盖规则
        └── AGENTS.md            # 被 override 文件覆盖，不会读取

5.3 合并规则

  • 文件从根目录向下拼接，用空行分隔
  • 离工作目录越近的文件，优先级越高（因为出现在后面）
  • 跳过空文件
  • 合并大小上限由 project_doc_max_bytes 控制（默认 64 KiB）

5.4 配置选项

在 ~/.codex/config.toml 中自定义：

# 添加备选文件名
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]

# 调整大小上限
project_doc_max_bytes = 65536

5.5 编写最佳实践

全局 AGENTS.md（~/.codex/AGENTS.md）：

# 通用规范

- 使用中文回复
- 代码注释用英文
- 提交信息使用 Conventional Commits 格式
- 优先使用 pnpm，不用 npm

5.8 Memories：Codex 自己记住的东西

5.9 迭代飞轮：越用越好的系统

AGENTS.md 不是一次性文档。它是一个活的系统，每一条规则背后都是一次真实踩过的坑。

这个过程是这样的：

  1. 第一周：空文件 — 你只写了基本的项目架构和开发命令。Codex 犯很多错。
  2. 第二周：护栏初现 — 你把 Codex 犯过的错一条条记下来。「不要在这个文件里用相对路径」「跑完迁移记得重新生成类型」。错误率开始下降。
  3. 第一个月：飞轮启动 — AGENTS.md 有了 20-30 条规则，都是真实的坑。Codex 的输出质量明显提升，你需要纠正的次数越来越少。
  4. 之后：持续迭代 — 偶尔加新规则，偶尔删掉过时的。文件保持精简但高度定制。
核心逻辑：Codex 犯错 → 记录到 AGENTS.md → 下次不再犯 → 错误率持续降低。每一条规则都对应一个真实踩过的坑，文件也天然保持精简——因为你只记录真正出过问题的地方。

这就是为什么说 AGENTS.md 是最重要的文件。用三个月养出来的那个文件，是你最有价值的 AI 资产。

6.6 推理强度：别省这个钱

Codex 支持调整模型的推理深度，控制执行任务时投入多少推理资源。

级别适合场景特点
low简单格式化、重命名快，但容易犯低级错误
medium日常开发任务默认级别，平衡速度和质量
high复杂功能开发、调试想得更深，需要返工的次数更少
 
model_reasoning_effort = "high"   # 复杂任务
# model_reasoning_effort = "medium" # 默认
# model_reasoning_effort = "low"    # 简单任务

很多人觉得「这个任务简单，调到 low 省点时间」。但 low 做错了，你纠正它花的时间可能比直接用 high 做对还长。

实用建议：默认用 medium 就好，不需要额外调整。别为了省几秒钟把推理强度调低，修低级错误花的时间远不止几秒。

6.7 Context Engineering：信息不是越多越好

Context 不只是你打的那句话。AGENTS.md 的内容、Codex 读过的文件、你粘贴的截图、对话历史，全部加起来都是 Context。

直觉上你可能觉得：给 Codex 的信息越多越好吧？

恰恰相反。上下文太多，模型表现反而变差。它会在海量信息中迷失，做出混乱的决策。建议定期检查上下文窗口的使用情况。

上下文管理的核心原则：不是给所有信息，而是给对的信息。让 Codex 看到它解决当前问题需要的上下文，而不是整个项目的百科全书。

你可以通过几种方式主动管理上下文：

  • @ 引用文件：在编辑器中用 @ 告诉 Codex 去读某个特定文件
  • 粘贴截图：UI 问题直接截图粘贴，比文字描述准确 10 倍
  • Pipe 数据：cat error.log | codex exec "分析这个日志" 直接把日志喂给 Codex
  • 给图片：codex -i screenshot.png "修复这个 UI 问题"

6.8 让 Codex 采访你

当你要做一个比较大的功能（比如从零搭建一个支付系统），不要一上来就写需求文档。先对 Codex 说：

我想做一个支付功能，在动手之前，先采访我，
问清楚所有你需要知道的事情。

Codex 会开始问你一系列问题：支持哪些支付方式？需要处理退款吗？并发量预估多少？需要支持 webhook 回调吗？用什么货币？

这些问题中，至少有一半是你自己没考虑过的。Codex 帮你做了需求分析师的工作。

采访结束后，让 Codex 把答案整理成一份 Spec（规格文档）。然后关键来了：开一个全新的会话，把 Spec 喂给新的 Codex，让它执行。

为什么要开新会话？因为采访过程中积累的对话历史已经很长了，占了大量上下文。新会话从一份干净的 Spec 开始，Codex 能更专注地执行，不会被中间讨论过程干扰。

6.9 把 Codex 当高级工程师提问

很多人只把 Codex 当写代码的工具。其实它同样是一个极好的代码库导航员。

你可以直接问它：

  • 「项目里的 logging 怎么工作的？」
  • 「怎么新建一个 API endpoint？」
  • 「src/lib/db.ts 和 src/utils/database.ts 有什么区别？为什么有两个？」

Codex 会读相关代码，然后给你一个结构化的解释。比读文档快，比问同事方便，尤其是刚接手一个新项目的时候。

Onboarding 加速器：加入一个新项目后，先花 10 分钟问 Codex：「这个项目的架构是什么？核心模块有哪些？数据流是怎么走的？」你会省下至少半天翻文档的时间。

6.10 多轮对话策略

和 Codex 的对话不是一次性的。你经常需要在多轮对话中逐步推进一个任务。这里有几个经过实战验证的策略：

紧密反馈循环

别等 Codex 写完 500 行代码再看结果。发现方向偏了，立刻纠正。越早纠正成本越低。Codex 写了 10 行时你说「不对，换个方式」，成本几乎为零。写完整个功能再推倒重来，浪费的是 tokens 和时间。

两次纠正不行，换条路

纠正了两次 Codex 还是不按你的意思来？别继续纠正了。/clear 清掉上下文，用一个更好的初始 prompt 重新开始。在一个已经跑偏的对话里纠缠，往往越绕越远。

换任务就清上下文

写完一个组件后要去改数据库 schema？/clear。不同任务有不同的上下文需求，把前一个任务的对话历史带进新任务只会增加噪音。

6.11 三个提问原则

和 Codex 对话的核心其实就三个字。

具体。文件名、行号、函数名、期望行为，能给就给。越具体的指令，越精确的输出。

指向。你代码库里一定有写得好的部分。把它们当参考范本指给 Codex 看。「像那个一样做」比「做一个漂亮的」有效 100 倍。

克制。一次只做一件事。任务大就分步来，每步确认结果后再下一步。一条消息里塞三个不相关的需求，Codex 大概率只做好其中一个。

这一章的核心：好的对话靠的不是花哨的 prompt，而是精准的上下文。具体化需求，让 Codex 采访你来补盲点，用 /clear 保持干净，别把 effort 调低。说到底，最有效的进阶是在实践中积累和 Codex 协作的直觉，不是学更多 prompt 技巧。

第 7 章  沙盒机制与安全模型

7.1 沙盒原理

沙盒不仅约束 Codex 本身，还约束它产生的所有子进程 —— git、包管理器、测试运行器等都继承相同的限制。

平台沙盒技术
macOSSeatbelt 框架
Linux / WSL2bubblewrap (bwrap)
Windows原生 Windows Sandbox 或 WSL2

7.2 三种沙盒模式

# 只读 —— 不能修改任何文件
codex -s read-only "审查代码安全性"

# 工作区写入（默认）—— 只能修改工作目录内的文件
codex -s workspace-write "重构这个模块"

# 完全访问 —— 无文件系统和网络限制（谨慎使用）
codex -s danger-full-access "运行 gh 命令"

7.3 扩展可写目录

不要为了一个例外就切换到 danger-full-access，可以在 config.toml 中精确授权额外的可写目录：

sandbox_mode = "workspace-write"

[sandbox_workspace_write]
writable_roots = ["/tmp/codex-output", "/var/log/app"]

7.4 网络访问

workspace-write 模式下网络默认被阻止。需要网络时：

codex -c 'sandbox_workspace_write.network_access=true' "安装依赖包"

7.5 Rules（规则）

使用规则对特定命令前缀设置策略，比粗粒度的沙盒模式更精确：

  • 允许特定命令自动执行
  • 对危险命令要求审批
  • 完全禁止某些命令

第四部分 · 扩展与协作

第 11 章  扩展能力：Skills、Hooks 与工具集成

用到后面你会发现，Codex 真正的价值不是它本身有多强，而是你能在它身上接多少东西。Skills、Hooks、MCP 三种扩展机制，让它从一个终端工具变成一个可以无限生长的工作台。

11.1 为什么需要扩展

你可能以为 Codex 装好就完事了。后来发现自己总在重复同样的话：每次提交代码前念叨一遍「先跑个 lint」、每次新建组件要交代一遍项目规范、每次查数据要手动复制 SQL 结果贴给 Codex。

这种重复一旦超过三次，就该想办法自动化了。Codex 提供了三种扩展机制，各自解决不同层面的问题：

机制本质确定性适用场景
SkillsMarkdown 指令包高但非 100%（advisory）领域知识、可复用工作流
HooksShell 脚本钩子100% 确定执行格式化、lint、安全检查
MCP外部工具协议100%连接数据库、Slack 等外部服务

三者的关系：Skills 教 Codex 怎么做事，Hooks 在关键节点自动执行检查，MCP 连接外部工具和数据源。

11.2 Skills：最值得先学的

Skills 是最容易上手的扩展方式。原理简单到有点不像话：在 .agents/skills/（项目级）或 ~/.codex/skills/（全局）目录下创建一个文件夹，放一个 SKILL.md 文件，Codex 就会根据上下文自动加载里面的指令。

.agents/skills/              # 项目级 skills（提交到 git）
├── react-component/
│   └── SKILL.md    # 创建 React 组件的规范和步骤
├── fix-issue/
│   └── SKILL.md    # 修 bug 的标准流程
└── deploy-preview/
    └── SKILL.md    # 部署预览环境的步骤

用 /skill-name 可以手动调用某个 skill，Codex 也会根据对话内容自动判断要不要加载。比如你说「帮我创建一个新的 React 组件」，Codex 会自动加载 react-component skill 里的规范。

两种类型的 Skills

知识型：告诉 Codex「这个项目里的事情应该怎么做」。比如 API 规范、编码风格、项目约定。这类 skill 更像文档，Codex 读完会按里面的规则办事。

工作流型：告诉 Codex「遇到这种任务按什么步骤执行」。比如 /fix-issue（修 bug 的标准流程）、/review-pr（代码审查流程）。这类 skill 更像 SOP，有明确的步骤和检查点。

一个挺实用的判断标准：如果一件事你每天做超过一次，就应该把它变成 skill 或 command。超过两次你就写了。

实际案例：创建 /techdebt 命令
把「发现技术债 → 评估影响 → 创建 issue → 关联到 sprint」这个流程写成 skill。以后发现技术债时，直接输入 /techdebt，Codex 会自动走完整个流程，包括评估优先级、创建 GitHub issue、加上正确的标签。

工作流型 skill 的关键配置

工作流型 skill 通常会执行有副作用的操作（比如创建 issue、发消息、部署）。SKILL.md 的 front matter 支持 name 和 description 字段，用于定义 skill 的名称和触发条件。通过精确设置 description，可以控制 Codex 何时自动加载该 skill。

---
name: deploy-preview
description: Deploy a preview environment for the current branch
---

手动调用时，使用 /skill-name 即可。

安装别人的 skill

Skills 可以共享。社区有不断增长的 skill 集合，你可以手动下载安装到全局 skills 目录：

mkdir -p ~/.codex/skills/community && \
curl -L -o ~/.codex/skills/community/SKILL.md \
  https://example.com/skills/api/install

安装后你就拥有了社区贡献的工作流，包括 commit 规范、PR 模板、代码审查标准等。

核心建议：写 skill 的最佳实践：从你最常对 Codex 说的那句话开始。如果你总是在提交前说「先跑一下测试，格式化一下代码，然后 commit」，那这就是一个 skill 的雏形。把这些步骤写进 SKILL.md，下次一个斜杠命令就搞定。

11.3 Hooks：不是建议，是强制

Skills 有一个天然的局限：它本质上是对 Codex 的「建议」。Codex 会尽量遵守，但遵从率不是 100%，尤其在长对话后期，它可能就忘了。大多数场景下够用，但有些事情你需要 100% 的确定性。

Hooks vs AGENTS.md：本质区别

很多人会把规则写在 AGENTS.md 里：「每次修改文件后请运行 npx eslint --fix」。这在大多数时候有效，但 Codex 偶尔会忘记，尤其在长对话、上下文被压缩之后。

AGENTS.md 是建议，Hooks 是强制执行。AGENTS.md 通过自然语言影响 Codex 的行为；Hooks 是 Codex 平台层面的机制，在特定生命周期节点触发 Shell 脚本，Codex 无法跳过或忽略。

生命周期钩子

Hooks 支持多个触发时机：

钩子触发时机典型用途
SessionStart会话启动时初始化环境、设置变量
PreToolUseCodex 调用工具之前拦截危险操作
PostToolUseCodex 调用工具之后自动格式化、自动测试
UserPromptSubmit用户提交提示词时预处理输入、注入上下文
StopCodex 完成回合时推动继续执行

实用案例

案例 1：自动格式化。每次 Codex 编辑文件后自动跑 eslint，不依赖 Codex「记住」要格式化。

// .codex/hooks.json
[
  {
    "event": "PostToolUse",
    "matcher": "Edit|Write",
    "command": "npx eslint --fix $CODEX_FILE_PATH"
  }
]

案例 2：推动 Codex 继续。有时候 Codex 会在一个复杂任务中途停下来问「要继续吗？」。Stop hook 可以检测这种情况，自动让 Codex 继续执行，适合无人值守的批处理场景。

案例 3：拦截危险操作。用 PreToolUse hook 在命令执行前进行检查，比如拦截 rm -rf 或 git push --force 等危险命令。

核心建议：你不需要自己从零写 hooks。直接告诉 Codex：「Write a hook that runs eslint after every file edit」，它会帮你生成配置并写入 .codex/hooks.json。Hooks 配置文件可以放在 ~/.codex/hooks.json（全局）或 <repo>/.codex/hooks.json（项目级别）。

11.4 Slash Commands：自定义快捷操作

除了 /skill-name 调用 skill，你还可以通过 Skills 机制创建类似「命令」的工作流。在 SKILL.md 中定义多步骤的执行流程，就能将复杂操作封装成一键命令。

下面是一个工作流型 Skill 的例子，将 commit → push → PR 封装成一个命令：

# .agents/skills/commit-push-pr/SKILL.md

帮我完成以下操作：

1. 查看当前的 git diff:
```bash
git diff --stat
```

2. 生成 commit message 并提交
3. 推送到远程分支
4. 创建 Pull Request，标题基于 commit 内容

注意：PR 描述要包含变更摘要。

输入 /commit-push-pr，Codex 就会按照这个流程自动执行。因为 skill 文件存在 .agents/skills/ 里，它会随 Git 一起提交，团队成员都能用。

知识型 vs 工作流型 Skill
两者都是 Skill，但定位不同。知识型 Skill 更像「规范文档」，Codex 根据上下文自动应用；工作流型 Skill 更像「宏」，强调执行流程和步骤。经验法则：如果需要 Codex「知道什么」，写知识型 skill；如果需要 Codex「做一串事」，写工作流型 skill。

11.5 组合使用：Skills + Hooks + MCP

Skills、Hooks、MCP 可以各自独立使用，但组合起来才真正厉害。

比如一个「代码智能」的扩展组合，可能同时包含：

  • 一个 skill：告诉 Codex 如何利用符号导航理解代码结构
  • 一个 hook：编辑后自动运行类型检查
  • 一个 MCP：连接语言服务器获取精确的符号信息

这三者配合，让 Codex 在理解和修改代码时更准确，而你只需要一次安装。

11.6 三种扩展机制的协作

实际项目中，三种机制经常协同工作。一个完整的例子：

假设你的团队有这样一个工作流：收到 bug 报告 → 定位问题 → 修复 → 跑测试 → 提交 PR → 通知相关人。

  • MCP（Slack）让 Codex 收到 bug 报告并能回复修复结果
  • Skill（fix-issue）指导 Codex 按标准流程定位和修复问题
  • Hook（PostToolUse）确保每次修改后都自动跑测试和格式化

单独用任何一个都有价值，组合起来就是一条完整的自动化 bug 修复流水线。

核心建议：不要想着一上来就搭一套完整的扩展体系。从你最痛的那个重复操作开始：总在口述规则？写个 skill。总忘记跑 lint？加个 hook。总在手动倒腾数据？接个 MCP。一个一个加，慢慢的你的 Codex 就变成了一个为你量身定制的工作台。

第 12 章  多 Agent 协作

Codex 最被低估的不是它写代码有多快，而是它可以同时跑很多个。学会并行之后，你的工作模式会从「一个人配一个 AI」变成「一个人指挥一支 AI 团队」。

12.1 一个人为什么要开那么多窗口

高效的 Codex 用户通常会同时开多个实例（独立的 git checkout），每个跑不同的任务。一个写新功能，一个修 bug，一个写测试，一个重构，一个做代码审查。同时进行。

原因很直接：Codex 的工作模式是「你给任务 → Codex 花几分钟执行 → 你 review 结果 → 给下一个任务」。中间有大量等待时间。只开一个 session，大部分时间你在等 Codex 干活。开多个 session，你 review 第一个的时候其他几个还在跑，等待时间大幅降低。

关键前提是：每个 session 需要在独立的代码环境中运行，否则它们会互相覆盖文件，制造冲突。这就是 Git Worktrees 要解决的问题。

12.2 Git Worktrees：并行的基础设施

Git Worktree 允许你从同一个仓库创建多个工作目录，每个工作目录在不同的分支上，文件系统完全隔离。你可以手动创建 worktree，然后在每个 worktree 中分别启动 Codex：

# 手动创建 worktree 并在其中启动 Codex
git worktree add ../project-fix fix/login-bug
cd ../project-fix && codex "修复登录问题"

# 另一个终端窗口
git worktree add ../project-feat feat/dashboard
cd ../project-feat && codex "实现 dashboard"

每个 worktree 是完全独立的文件系统，多个 Codex 实例不会互相干扰。完成后你可以把分支合并回主分支，然后清理 worktree。

配合 Tmux 使用

用 Tmux 管理多个 Codex session，可以用快捷键在不同 session 之间切换：

# ~/.zshrc 中添加
alias za="tmux select-window -t codex:0"
alias zb="tmux select-window -t codex:1"
alias zc="tmux select-window -t codex:2"

za 跳到第一个 session，zb 跳到第二个，以此类推。

12.3 Subagents：给主 session 叫个帮手

并行 session 适合处理互不相关的独立任务。但有时候你要的不是开一个新窗口，而是在当前任务中调一个「专家」来处理特定环节，比如让一个安全审查专家 review 你刚写的认证代码。这就是 Subagents 干的事。

Subagents 让主 session 可以调用具有独立上下文的子代理来处理特定环节。比如安全审查 agent 可以配置为只有读权限（不能改代码），专注于 review 任务。

Subagents 的核心价值

Subagents 最重要的特性不是「专业分工」，而是独立上下文。

每个 subagent 运行在自己的上下文窗口中，不消耗主 session 的上下文空间。当主 session 的对话已经很长、上下文快要满了的时候，调用一个 subagent 来处理子任务，相当于开了一个新的「思考空间」，不会挤压主 session 的容量。

核心建议：实用的 subagent 组合：security-reviewer（每次涉及认证、权限、数据存储时自动调用）+ verify-app（修改完成后自动启动应用并验证功能是否正常）。这两个覆盖了「写得对不对」和「跑得起来吗」两个最常见的验证需求。

12.4 Agent Teams：让它们自己协调

Worktrees 让你手动管理多个并行 session。Subagents 让主 session 调一个专家。Agent Teams 更进一步：多个 session 之间能互相通信、协调分工。

Writer/Reviewer 模式

最经典的用法是一个写代码、另一个审代码：

  1. Writer Agent 写代码 — 负责实现功能，按照需求写代码、跑测试
  2. Reviewer Agent 审代码 — review Writer 的输出，指出问题、建议改进
  3. Writer 根据反馈修改 — 收到 review 意见后改进代码，形成迭代循环

这个模式比单个 agent 写代码好不少。原因和人类团队一样：写代码的人容易陷入自己的思路，审代码的人能从不同角度发现问题。两个 agent 互相盯着，产出质量肉眼可见地提升。

测试驱动模式

另一个高效的模式：一个 agent 写测试，另一个写实现。写测试的 agent 先根据需求定义「什么是正确行为」，写出测试。然后写实现的 agent 再去满足这些测试。这就是 AI 版的 TDD（Test-Driven Development）。

12.5 Fan-out 批处理：人海战术的 AI 版

前面都是几个 agent 配合做一件事。Fan-out 模式解决的是另一类问题：同一个操作需要对大量文件重复执行。

非交互模式

Codex 支持非交互模式，用 codex exec 命令传入 prompt，适合在脚本中调用：

# 非交互模式执行单个任务
codex exec "把这个文件从 JavaScript 迁移到 TypeScript"

配合 shell 循环，你可以批量处理：

# 批量迁移一批文件
for file in $(cat files-to-migrate.txt); do
  codex exec --full-auto "Migrate $file from JS to TS" &
done

注意末尾的 &：这让每个 Codex 实例在后台并行运行。如果有 50 个文件要迁移，50 个 Codex 同时跑，可能几分钟就完成了原本需要一整天的迁移工作。

批量脚本模式

你可以写一个简单的 shell 脚本来管理批量任务：

  1. 规划阶段 — 先用 Codex 交互模式分析项目，列出需要处理的文件清单
  2. 批量执行 — 用 shell 循环配合 codex exec 并行执行
  3. 汇总结果 — 检查各实例的退出码和输出，处理失败的 case

12.6 不一定要盯着电脑

前面说的都是本地终端操作。但 Codex 也支持远程和异步执行，不用一直守在终端前面。

非交互批量任务

对于需要定期执行的任务（依赖更新、安全扫描），可以通过 codex exec 配合系统的 cron 或 CI/CD 调度来实现自动化，无需一直守在终端前面。

核心建议：从 2 个 session 开始就好。不用一上来就开 10 个。先习惯在两个之间切换：一个做主任务，另一个做辅助的（写测试、做 code review）。等觉得游刃有余了再加。

每个 session 给一个明确的角色。用 git 分支隔离一切。并行不等于不管 — 每隔 15-20 分钟看看各个 session 的进度，及时纠偏。

14.1 GitHub Actions 集成

name: Codex auto-fix on CI failure

on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]

jobs:
  auto-fix:
    if: ${{ github.event.workflow_run.conclusion == 'failure' }}
    runs-on: ubuntu-latest
    env:
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
    steps:
      - uses: actions/checkout@v4
      - run: npm i -g @openai/codex
      - run: printenv OPENAI_API_KEY | codex login --with-api-key
      - run: |
          codex exec --full-auto --sandbox workspace-write \
            "运行测试，找出失败原因，实施最小修复"

第 16 章  从零构建一个完整产品

前面所有章节讲零件，这一章组装。用一个真实项目把前面学的东西全串起来，你会发现 Codex 真正的威力不在于某个单一功能，而在于它们连起来之后的化学反应。

16.1 Phase 0：先别急着写代码

很多人一开始做产品时犯过一个错：想到什么就立刻让 Codex 开始写代码。结果做到一半发现需求没想清楚，只能推翻重来。

后来养成了一个习惯：先让 Codex 采访你。它其实很擅长这个。

我想做一个周报工具，在动手之前，先采访我，
问清楚所有你需要知道的事情。一次问一个问题。

Codex 会开始像产品经理一样采访你：

  • 目标用户是谁？（个人开发者？还是团队？）
  • 核心功能有哪些？（只生成周报？还是也需要分享？）
  • 技术偏好？（部署到哪里？用什么框架？）
  • 有没有设计参考？（周报长什么样？）

回答完这些问题后，让 Codex 把结论整理成一份规格文档（SPEC.md）。然后关键来了：开一个全新的会话，把 SPEC 喂给新的 Codex，让它执行。

为什么要开新会话？因为采访过程中积累的对话历史已经很长了，占了大量上下文。新会话从一份干净的 SPEC 开始，Codex 能更专注地执行。

16.2 Phase 1：项目初始化

新 session，干净的开始。一句话创建项目骨架：

Create a Next.js project called weekly-report with Tailwind CSS.
Set up the basic folder structure following SPEC.md requirements.
Include TypeScript, and configure ESLint.

Codex 会执行一连串操作：运行 npx create-next-app、安装依赖、配置 Tailwind、创建基础目录结构。

接下来是关键一步：配置 AGENTS.md。这是 §05 整章的核心，现在是实战：

# WeeklyReport

## Project Overview
AI-powered weekly report generator. Connects to GitHub,
summarizes commits with AI, generates shareable report pages.

## Tech Stack
- Next.js 15 (App Router) + TypeScript
- Tailwind CSS for styling
- NextAuth.js for GitHub OAuth

## Code Style
- Use server components by default, 'use client' only when needed
- API routes in app/api/, use Route Handlers
- Prefer named exports

## Testing
- Run `npm run lint` before committing
- Test API routes with curl before building UI

16.3 Phase 2：正式开发

到这里才真正开始写代码。先用 Plan 模式聊一轮架构，不急着动手。在终端里输入 /plan 切换到 Plan 模式：

"I need to implement the core flow: GitHub OAuth login → fetch this
week's commits → send to API for summarization → display the report.
Let's discuss the architecture before coding."

Codex 会给出一个完整的技术方案：API 路由如何设计、数据流怎么走、组件怎么拆分。你可以在这个阶段提出疑问、调整方案。

确认方案后，退出 Plan 模式，让 Codex 开始实现。每完成一个模块，做一次验证：

  1. GitHub OAuth — 让 Codex 跑 npm run dev，打开浏览器点登录按钮，看能不能跳转到 GitHub 授权页面
  2. 数据获取 — 登录成功后，用 curl 测试 API 路由，看返回的数据是否正确
  3. AI 总结 — 拿真实的数据调用总结接口，检查 AI 生成的周报内容是否合理
注意：每做完一步就验证，这是踩过最多坑之后总结出来的最重要的习惯。不要让 Codex 一口气写完所有代码再测。问题越早发现越容易修。

16.4 Phase 3：让它好看起来

功能跑通了，但界面大概率很丑。正常。先让功能跑起来，再管好不好看。

Codex 支持图片输入。最直接的方式：截一张当前页面的图，粘贴给 Codex：

看一下当前报告页面的截图。
问题：1) 标题区域太拥挤 2) 列表需要更好的间距
3) 右上角加一个分享按钮

Codex 会看到你的截图，理解当前的视觉问题，然后精准修改对应的 CSS 和组件代码。

核心建议：UI 打磨阶段最高效的做法是：先把所有问题一次性列出来，让 Codex 批量修改，而不是改一个看一个。批量反馈能让 Codex 更好地理解整体设计意图。

16.5 Phase 4：扩展能力实战

核心产品已经能用了。现在是 §11 内容的实战时间：给项目加上 Skills、MCP 和 Hooks。

创建一个 Skill — 每次想生成周报，都要打开项目、执行一串操作。能不能一句话搞定？可以，用 Skill。

在项目根目录创建 .agents/skills/generate-report/SKILL.md：

# /weekly-report

Generate this week's report.

## Steps
1. Run the dev server if not running
2. Call /api/github to fetch commits since last Monday
3. Call /api/summarize to generate the report
4. Open the report page in browser
5. Show the shareable URL

配置完成后，在任何 Codex session 中输入 /weekly-report，它就会自动执行以上所有步骤。一个命令，10 秒出周报。

添加 MCP：连接 Slack — 周报生成了，手动发到 Slack 频道太麻烦。用 MCP 把两者打通。

设置 Hook：自动 Lint — 每次 Codex 执行 git commit 时，都会先确保代码质量。这是 §11 里 Hook 的典型用法：在关键节点注入自动检查。

16.6 Phase 5：部署上线

产品在本地跑得好好的，该让全世界都能访问了。

variables for GitHub OAuth and API key.
Also create a GitHub Actions workflow that runs lint
and type check on every PR.

Codex 会执行部署命令、配置环境变量、创建 CI/CD 配置文件。整个过程你不需要手动打开 Vercel 的 dashboard，也不需要手写 GitHub Actions 的 YAML。

如果从头到尾比较顺利，整个过程大概需要 5-8 个小时。其中最耗时的是 Phase 2（核心功能开发），OAuth 配置和 API 调试需要反复验证。

我踩出来的几条经验：
一、需求拆小，每次只给一步。先做登录，确认能跑。再做数据存储，确认能存能取。然后是核心业务逻辑，然后才是 UI。每一步验证通过，再进下一步。
二、先跑通最小功能，再一步步加。第一个版本只有一个功能：打开 App，屏幕变白，亮度拉满。就这么简单。确认补光效果还行，才开始加色温调节、亮度滑块这些功能。
三、验证比开发更重要。AI 生成的代码需要验证，就像人写的代码需要测试一样。每完成一个功能模块，立刻打开浏览器或跑测试。发现问题立刻修，不要积累。
四、不要在一个 session 里做太多不相关的事。我通常这样分 session：项目初始化 + 基础架构 / 核心后端逻辑 / 前端页面和交互 / 测试和 bug 修复 / 部署和 CI/CD。
五、产品感知才是你最大的杠杆。Codex 能帮你写代码、调 UI、配部署、修 bug。但它帮不了你决定：这个产品到底应该解决什么问题？目标用户是谁？什么功能该做什么功能该砍？这些是产品判断。

第 17 章  心智模型与持续进化

工具会过时，功能会更新。但好的思维方式不会贬值。最后一章退后一步，聊几个比具体操作更重要的东西。

17.1 三层模型：你的时间该花在哪

讲了这么多具体操作，现在值得建立一个全局视角。Codex 的所有能力，其实可以归入三个层次：

层次投入方式回报特征
Prompt 层每次对话都要重新投入一次性回报
Context 层写一次 AGENTS.md，持续生效复利回报
Harness 层搭一次自动化流程，永久运行指数回报

Prompt 层是你在终端里输入的每一句话。「帮我加一个登录页面」「这个 bug 修一下」。大多数初学者的全部交互都停留在这一层。它有效，但每次都需要你开口，每次都从零开始。

Context 层是 Codex 在回答你之前已经「看到」的所有信息。AGENTS.md 文件、项目的文件结构、git 提交历史、package.json 里的依赖列表。这些信息不需要你每次重复，Codex 会自动读取。§05 讲的 AGENTS.md，本质上就是在优化这一层。

Harness 层是你构建的自动化环境。Skills 让你把常用工作流封装成可复用的指令；Hooks 让特定事件自动触发操作；MCP 连接外部服务；Agent Teams 让多个 Codex 实例并行协作。这一层的特点是：一旦搭好，它就一直在工作，不需要你每次手动触发。

一个比喻：Prompt 是你开口说话，Context 是你提前准备好的 PPT，Harness 是你搭建的整个舞台。观众（Codex）的表现，取决于这三层的综合质量。

初学者把所有精力都花在 Prompt 层，反复琢磨措辞、研究提示词技巧。这没有错，但天花板很低。高手的做法是：尽量把信息沉淀到 Context 层，把重复劳动交给 Harness 层，只在 Prompt 层处理真正需要临时决策的事情。

如果你读完这本手册只记住一件事，就记住这个：把时间花在构建 Context 和 Harness 上，而不是优化 Prompt。

17.2 引擎盖下的 Codex

用了这么久 Codex，你有没有好奇过：当你按下回车之后，到底发生了什么？

核心循环：Think → Act → Observe → Repeat

Codex 的核心是一个典型的 Agent 循环。你在终端里输入一句话后发生的所有事情，都是这个循环在驱动：

  1. Think — 分析当前状态，决定下一步做什么
  2. Act — 调用一个工具执行操作（比如读一个文件、运行一条命令）
  3. Observe — 读取返回的结果，判断任务是否完成
  4. Repeat — 未完成就回到 Think 继续循环

先思考当前状态、决定下一步做什么；然后调用一个工具执行操作；观察返回的结果，判断任务是不是完成了；没完成就回到 Think 继续循环。整个过程可能转几十圈才停下来。

这就解释了为什么 Codex 有时候看起来「绕弯路」。它不是一个从输入到输出的直线程序，它是一个不断试探和调整的循环体。每一步都在根据新的观察做决策。有时候它试了一个方案发现不行，回退换另一条路，这其实是设计的一部分，不是 bug。

也正因如此，给 Codex 明确的验证标准特别重要。循环需要一个停止条件。如果你的需求描述模糊，它不知道什么时候算「做完了」，就会不停地循环下去，改来改去。告诉它「测试通过就停」或「生成文件就行」，它收敛的速度会快很多。

40+ 工具，4 个能力原语

Codex 内部有 40 多个工具，每个都有独立的权限控制。但如果你退后一步看，所有能力其实归结为 4 个原语：

原语做什么典型工具
Read读文件、读代码、搜索内容Read、Grep、Glob
Write写文件、编辑代码Write、Edit
Execute运行命令、执行脚本Bash
Connect连接外部服务MCP 工具、WebFetch

这个设计挺巧妙的，关键在 Bash 工具。它是一个万能适配器，让 Codex 能使用人类开发者的一切命令行工具。不需要给每种编程语言做专门集成，通过 Execute + Bash 就能操作一切。这也是 Codex 能在几乎任何技术栈的项目里工作的原因。

17.3 身份在变：从写代码到构建产品

这个变化比大多数人预期的要快。

越来越多的工程师公开表示，自己超过 90% 的代码都由 AI 生成。他们的日常更多是：描述需求、审查输出、做架构决策。有人总结得挺精辟：「我现在的工作更像是一个有技术判断力的产品经理。」

这意味着关键能力正在发生转移：

旧能力（重要性下降）新能力（重要性上升）
语法熟练度需求拆解能力
框架 API 记忆架构判断力
手动调试技巧输出质量评审
代码模板积累产品品味

注意，说的是「重要性下降」而不是「没用」。理解代码仍然有价值，它能帮你更好地描述需求、更准确地评审输出。但你不再需要能从零手写一个完整应用，你需要的是能判断一个应用写得好不好。

这个转变的核心问题是：从「怎么写」到「写什么」。

以前，你可能花 80% 的时间在「怎么实现这个功能」上，20% 在「应该做什么功能」上。现在比例倒过来了。Codex 解决了「怎么写」的问题，但「写什么」这个问题，它帮不了你太多。你需要自己想清楚：这个产品解决什么问题？目标用户是谁？核心体验是什么？哪些功能必须有，哪些可以砍掉？

核心建议：如果你正在焦虑「AI 会不会取代我」，可以换个角度想：学会定义需求、设计交互、评审质量。这些能力不会因为 AI 变强而贬值。

17.4 迭代这么快，怎么跟

真正该关注的不是具体功能变化，而是方向。过去一年半的演进，有三条线索始终没变：

  1. 自主性持续增强。从需要你逐步指令，到能自主规划和执行。
  2. 上下文窗口持续扩大。从 8K 到 200K 到 1M，Codex 能「看到」的项目规模越来越大。
  3. 协作模式持续丰富。从单 Agent 到 SubAgents 到 Agent Teams，多 Agent 协作越来越自然。

这意味着你今天学的「怎么和 AI 协作」不会过时。具体命令可能变，但「描述需求→审查输出→迭代改进」这个核心循环，在可预见的未来不会变。

最后一条建议：别花太多时间研究工具，去构建东西。找一个你真正想解决的问题，打开终端，开始和 Codex 对话。遇到卡住的地方翻翻这本手册，翻完继续做。

从想法到产品的距离，现在短到你可能还不太适应。

附录 C  常见问题

Codex CLI 免费吗？
ChatGPT Plus/Pro/Business/Edu/Enterprise 订阅用户可以免费使用。也可以使用 OpenAI API Key 按量付费。
支持哪些操作系统？
macOS 和 Linux 完全支持。Windows 需要 WSL2，目前为实验性支持。
如何使用本地开源模型？
安装 Ollama 后，使用 codex --oss 即可使用本地模型。
AGENTS.md 和 CLAUDE.md 有什么区别？
AGENTS.md 是 Codex（OpenAI）使用的项目指令格式，CLAUDE.md 是 Claude Code（Anthropic）使用的。两者功能类似，都是给 AI 编程代理提供项目规范。AGENTS.md 已成为由 Agentic AI Foundation（隶属 Linux Foundation）管理的跨工具开放标准。
沙盒会影响性能吗？
沙盒使用 OS 原生机制（macOS Seatbelt / Linux bubblewrap），性能开销极小。
如何在团队中共享配置？
将 .codex/config.toml 和 AGENTS.md 提交到代码仓库中。项目级配置在团队成员间自动共享。
codex exec 输出到哪里？
进度信息输出到 stderr，最终代理消息输出到 stdout，方便管道操作和重定向。
如何回退 Codex 的修改？
建议在使用前创建 Git checkpoint。使用 git diff 查看变更，git checkout . 回退。
